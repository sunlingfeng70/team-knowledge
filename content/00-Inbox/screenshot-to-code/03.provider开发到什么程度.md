## screenshot-to-code的provider没有更抽象，是指它里面就三个模型的分支吗？分别开发了不同的代码?  





不是“里面只有三个模型分支”，更准确地说是：

> 它有三个 Provider 实现，分别对应 OpenAI、Anthropic、Gemini；每个 Provider 下面又可以配置多个模型。三份代码主要处理各家 API 协议差异，不是三套独立的业务生成逻辑。

结构可以画成：

```
统一 Agent Engine
        |
        v
Provider Factory
        |
  +-----+----------+
  |                |
OpenAI          Anthropic          Gemini
Provider        Provider           Provider
Session         Session            Session
  |                |                  |
OpenAI API       Anthropic API       Gemini API
```

相关代码在：

- [factory.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/factory.py)
- [openai.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/openai.py)
- [anthropic/provider.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/anthropic/provider.py)
- [gemini.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/gemini.py)

## 不是三个模型，而是三个模型供应商

例如 OpenAI 下面可能有：

```
GPT-5.4 Mini
GPT-5.4
GPT-5.5
GPT-5.6
```

Anthropic 下面可能有：

```
Claude Sonnet
Claude Opus
Claude Fable
```

Gemini 下面可能有：

```
Gemini Flash
Gemini Pro
```

代码中的 `Llm` 枚举把“具体模型”和“推理强度”组合在一起，例如：

```
Llm.GPT_5_5_HIGH
Llm.GEMINI_3_1_PRO_PREVIEW_HIGH
Llm.CLAUDE_OPUS_5_MAX
```

然后通过映射判断它属于哪个 Provider：

```
MODEL_PROVIDER: dict[Llm, str] = {
    ...
}
```

Provider 工厂再按集合分支：

```
if model in OPENAI_MODELS:
    return OpenAIProviderSession(...)

if model in ANTHROPIC_MODELS:
    return AnthropicProviderSession(...)

if model in GEMINI_MODELS:
    return GeminiProviderSession(...)
```

所以分支判断的粒度是：

```
model -> provider
```

而不是：

```
每个模型都实现一套独立代码
```

## 三个 Provider 分别开发了哪些代码？

它们各自实现的是“供应商适配层”。

统一接口定义在：

[base.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/base.py)

大致包括：

```
class ProviderSession(Protocol):
    async def stream_turn(self, on_event):
        ...

    async def append_tool_results(self, turn, executed_tool_calls):
        ...

    def total_cost_usd(self):
        ...

    async def close(self):
        ...
```

这几个方法是 Agent Engine 依赖的统一接口。

每家 Provider 都实现这些方法，但内部写法不同。

### OpenAI Provider

[openai.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/openai.py)

使用 OpenAI Responses API：

```
stream = await self._client.responses.create(...)
```

主要负责：

- 把内部工具定义转换为 OpenAI function tool schema
- 解析 OpenAI Responses API 的流式事件
- 识别文本增量
- 识别 reasoning/thinking 增量
- 识别 function call 增量
- 把工具结果转换成：

```
{
  "type": "function_call_output",
  "call_id": "...",
  "output": "..."
}
```

### Anthropic Provider

[provider.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/anthropic/provider.py)

使用 Anthropic Messages API：

```
async with self._client.messages.stream(...) as stream:
```

主要负责：

- 把工具定义转换成 Anthropic 的 `tools` 格式
- 解析 Anthropic 的 `content_block_delta`
- 处理 `tool_use`
- 处理文本 block
- 继续对话时追加：

```
assistant:
  text block
  tool_use block

user:
  tool_result block
```

Anthropic 的工具结果协议和 OpenAI 不一样，所以不能直接复用 OpenAI 的 continuation 代码。

### Gemini Provider

[gemini.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/gemini.py)

使用 Gemini SDK：

```
stream = await self._client.aio.models.generate_content_stream(...)
```

主要负责：

- 把工具定义转换成 Gemini function declaration
- 解析 Gemini 的流式内容
- 处理 Gemini 的 function call
- 保存 Gemini 原始 model content
- 用 `Part.from_function_response(...)` 追加工具结果

Gemini 的上下文结构、Part、函数响应以及 thought signature 等机制和前两者不同，因此也必须有单独的协议处理。

## 哪些代码是共享的？

真正的业务生成逻辑没有复制三份，主要集中在这些地方：

### 1. Agent Loop 共享

[engine.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/engine.py)

它只依赖统一对象：

```
ProviderSession
ProviderTurn
StreamEvent
ToolCall
ExecutedToolCall
```

核心循环是同一份：

```
for _ in range(max_steps):
    turn = await session.stream_turn(on_event)

    if not turn.tool_calls:
        return await self._finalize_response(turn.assistant_text)

    for tool_call in turn.tool_calls:
        tool_result = await self.tool_runtime.execute(tool_call)

    await session.append_tool_results(turn, executed_tool_calls)
```

这段代码不会写：

```
if openai:
    ...
elif anthropic:
    ...
elif gemini:
    ...
```

模型厂商差异被 Provider 层吸收了。

### 2. 工具定义共享

[definitions.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/tools/definitions.py)

工具只定义一份，例如：

```
create_file
edit_file
generate_images
extract_assets
screenshot_preview
```

然后不同 Provider 分别序列化：

```
CanonicalToolDefinition
  -> serialize_openai_tools(...)
  -> serialize_anthropic_tools(...)
  -> serialize_gemini_tools(...)
```

也就是：

```
一份业务工具定义
        |
        +--> OpenAI 格式
        +--> Anthropic 格式
        +--> Gemini 格式
```

### 3. 工具执行共享

工具真正执行的位置是：

```
backend/agent/tools/runtime.py
```

例如 `create_file` 到底如何修改内存文件状态、`edit_file` 如何做字符串替换、`screenshot_preview` 如何调用 Playwright，这些不属于 Provider。

无论模型来自哪家，最后都走：

```
tool_runtime.execute(tool_call)
```

## 为什么不能只写一份 Provider 代码？

因为三家的底层 API 并不是同一个协议。

差异主要有四类。

### 1. 请求格式不同

OpenAI 使用 Responses API 的 item/input 结构。

Anthropic 使用 messages/content blocks。

Gemini 使用 contents/parts/function declarations。

### 2. 流式事件名称和结构不同

三家返回的流事件字段完全不同。

统一层希望看到：

```
assistant_delta
thinking_delta
tool_call_delta
```

Provider 需要把自己的原始事件转换成这些标准事件。

### 3. 工具定义格式不同

同一个工具，在三家 API 中大致会被表达成不同格式：

```
OpenAI:
  type=function
  function={name, description, parameters}

Anthropic:
  name
  description
  input_schema

Gemini:
  function_declarations
  parameters
```

所以必须有三个 serializer。

### 4. 工具结果回传格式不同

这是最不能硬复用的地方。

OpenAI：

```
{
  "type": "function_call_output",
  "call_id": "...",
  "output": "..."
}
```

Anthropic：

```
{
  "type": "tool_result",
  "tool_use_id": "...",
  "content": "..."
}
```

Gemini：

```
Part.from_function_response(...)
```

因此三个 Provider 中确实分别开发了不同代码，但这些代码是“协议适配代码”，不是“截图转代码业务代码”。

## 这个抽象做得够不够好？

可以评价为：

> 有抽象，但抽象层次比较窄，属于“够用型 Provider Adapter”，还不是 Pi 那种独立、通用的 LLM Runtime。

它已经抽象了：

```
ProviderSession
ProviderTurn
StreamEvent
ToolCall
ToolResult
```

但没有进一步抽象成一个独立的通用 AI SDK。例如：

```
Agent Engine
  -> ProviderSession
       -> OpenAI / Anthropic / Gemini
```

而不是：

```
通用 LLM SDK
  -> Message model
  -> Tool model
  -> Stream model
  -> Provider registry
  -> Model catalog
  -> Retry policy
  -> Auth policy
  -> Transport abstraction

业务 Agent
  -> 调用通用 LLM SDK
```

Screenshot-to-Code 的 Provider 代码仍然和本项目的 Agent、工具、成本统计、生成流程耦合较紧。

## 和 Pi 的抽象差别

可以用下面的方式理解：

### Screenshot-to-Code

```
项目内部抽象：

ProviderSession
  -> OpenAIProviderSession
  -> AnthropicProviderSession
  -> GeminiProviderSession
```

目标是：

```
让这个网页生成器同时支持三家模型
```

### Pi

```
独立的 pi-ai：
  统一模型 API、消息、流式事件、Provider

独立的 pi-agent-core：
  通用 Agent Loop、状态、工具调用、session

coding-agent：
  read / bash / edit / write 等具体工具
```

目标是：

```
让其他应用也可以复用这套 Agent 和 LLM 抽象
```

所以 Screenshot-to-Code 不是没有抽象，而是：

```
抽象存在，但停留在应用内部
```

Pi 则把抽象提升成了可独立发布的基础库。

------

## 最准确的一句话

你的理解可以修正为：

> Screenshot-to-Code 不是为三个模型分别写了三套代码，而是为三个模型供应商分别写了 API 适配器。上层的 Agent 循环、工具执行、文件状态和网页生成逻辑是共享的；各 Provider 只负责把 OpenAI、Anthropic、Gemini 的请求、流式响应、工具 schema 和工具结果转换成统一内部协议。

可以进一步拆成：

```
共享部分：
  Prompt
  Agent Loop
  Tool Runtime
  File State
  WebSocket Event
  业务规则

Provider 独有部分：
  SDK Client
  请求格式
  流式事件解析
  工具 schema 序列化
  工具结果续接
  token/cost 读取
  provider-specific workaround
```

所以如果你要借鉴它，建议采用这个边界：

```
业务 Agent 不判断具体厂商
Provider Adapter 不负责业务生成
```

而不是把所有代码都按：

```
if openai:
    生成 HTML
elif anthropic:
    生成 HTML
elif gemini:
    生成 HTML
```

这样会很快变成三套难以维护的业务分支。
