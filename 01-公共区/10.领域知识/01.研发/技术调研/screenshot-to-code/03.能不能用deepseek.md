## 也就是如果想使用deepseek的话，还需要专门为deepseek开发一个provider是吧



![image-20260911155912214](img/image-20260911155912214.png)

![image-20260911160832829](img/image-20260911160832829.png)



是的，按 Screenshot-to-Code 当前的架构，如果要正式支持 DeepSeek，通常需要新增一个 DeepSeek Provider，或者确认它是否能完全兼容现有的 OpenAI Provider。

关键不在于“模型名字不同”，而在于 DeepSeek 的 API 是否与现有 Provider 的协议、流式事件和工具调用行为兼容。

## 情况一：DeepSeek 兼容 OpenAI API

这是最简单的情况。

DeepSeek 提供 OpenAI-compatible API，通常可以复用 OpenAI Provider，只需要增加：

```
DeepSeek 模型配置
DeepSeek API Base URL
DeepSeek API Key
模型到 OpenAI Provider 的映射
```

例如逻辑上可能是：

```
if model in OPENAI_COMPATIBLE_MODELS:
    return OpenAIProviderSession(
        client=AsyncOpenAI(
            api_key=deepseek_api_key,
            base_url="https://api.deepseek.com"
        ),
        model=model,
        ...
    )
```

也就是说：

```
DeepSeek 模型
  -> OpenAI-compatible Provider
  -> DeepSeek API
```

这种情况下不一定要新建 `deepseek.py`。

但要注意，不能只看“接口长得像 OpenAI”，还要验证：

- 是否支持当前使用的 Responses API
- 是否只支持 Chat Completions API
- 是否支持工具调用
- 流式 tool call 参数是否按预期返回
- 是否支持多模态图片输入
- reasoning 字段如何返回
- 工具调用后的续接格式是否兼容
- token usage 字段是否兼容
- 是否支持当前的 `response_format` 或其他参数

Screenshot-to-Code 当前 OpenAI Provider 使用的是 Responses API：

```
stream = await self._client.responses.create(...)
```

如果 DeepSeek 只兼容 OpenAI Chat Completions，而不兼容 Responses API，那么就不能直接复用当前这一份 OpenAI Provider。

------

## 情况二：DeepSeek 只兼容 Chat Completions

如果 DeepSeek 支持：

```
client.chat.completions.create(...)
```

但不支持：

```
client.responses.create(...)
```

那么有两种做法。

### 做法 A：扩展 OpenAI Provider

把 OpenAI Provider 再抽一层：

```
统一 Agent Provider 接口
        |
        +--> OpenAI Responses Adapter
        +--> OpenAI Chat Completions Adapter
        +--> Anthropic Adapter
        +--> Gemini Adapter
```

然后 DeepSeek 走 Chat Completions Adapter。

### 做法 B：单独开发 DeepSeek Provider

新增：

```
backend/agent/providers/deepseek.py
```

实现统一接口：

```
class DeepSeekProviderSession(ProviderSession):
    async def stream_turn(...)
    async def append_tool_results(...)
    def total_cost_usd(...)
    async def close(...)
```

这份代码会负责：

```
DeepSeek 请求构造
DeepSeek 流式响应解析
DeepSeek 工具调用解析
DeepSeek 工具结果续接
DeepSeek token 统计
```

但是上层的 Agent Loop 不需要修改。

------

## 情况三：DeepSeek 具备特殊协议或能力限制

如果 DeepSeek 在以下方面与 OpenAI 差异较大，就应该单独 Provider：

- tool call 结构不同
- reasoning content 单独放在特殊字段
- 工具调用参数经常分片不完整
- 工具调用 ID 格式不同
- 续接对话需要特殊消息结构
- 不支持图片输入
- 不支持某些工具 schema
- token usage 字段不同
- 有特殊的 thinking/reasoning 参数

这时新增 Provider 会更清晰：

```
DeepSeekProviderSession
```

但仍然只新增“适配层”，不需要复制：

- Prompt 构造
- Agent Loop
- 工具执行
- 文件管理
- 截图预览
- 前端 WebSocket 协议

## 需要改哪些地方？

以当前项目为例，可能涉及这些位置。

### 1. 增加模型枚举

[backend/llm.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/llm.py)

例如：

```
class Llm(Enum):
    DEEPSEEK_V3 = "deepseek-v3"
    DEEPSEEK_REASONER = "deepseek-reasoner"
```

实际模型名要以 DeepSeek API 当前支持的名称为准。

### 2. 增加 Provider 分类

目前有：

```
OPENAI_MODELS
ANTHROPIC_MODELS
GEMINI_MODELS
```

可以新增：

```
DEEPSEEK_MODELS
```

或者把 DeepSeek 归入：

```
OPENAI_COMPATIBLE_MODELS
```

### 3. 增加 Key 和 Base URL 配置

例如：

```
DEEPSEEK_API_KEY
DEEPSEEK_BASE_URL
```

如果复用 OpenAI SDK，也可以使用 DeepSeek 的 Base URL。

### 4. 修改 Provider Factory

如果 DeepSeek 需要独立实现：

```
if model in DEEPSEEK_MODELS:
    return DeepSeekProviderSession(...)
```

如果完全兼容 OpenAI：

```
if model in OPENAI_COMPATIBLE_MODELS:
    return OpenAIProviderSession(...)
```

### 5. 实现工具 Schema 序列化

如果协议不同，需要：

```
serialize_deepseek_tools(...)
```

如果 DeepSeek 使用标准 OpenAI function schema，可以复用：

```
serialize_openai_tools(...)
```

### 6. 增加模型选择策略

[backend/routes/model_choice_sets.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/routes/model_choice_sets.py)

需要决定：

```
哪些 API Key 存在时选择 DeepSeek
创建任务是否使用 DeepSeek
更新任务是否使用 DeepSeek
是否把 DeepSeek 加入 variant
视频模式是否排除 DeepSeek
```

DeepSeek 通常不能替代 Gemini 的视觉能力，所以截图输入时要特别注意：

```
DeepSeek 负责代码生成
Gemini 负责视觉资产提取
```

## DeepSeek 最大的实际限制：视觉能力

Screenshot-to-Code 不是纯文本代码生成，它依赖视觉输入。

项目里有两类模型任务：

```
视觉任务：
  理解截图
  定位图片和 logo
  提取真实资产

代码任务：
  生成 HTML/CSS/React
  修改已有代码
  根据截图预览修复布局
```

如果你接入的 DeepSeek 模型不支持图片输入，那么它不能直接替换 Gemini/Claude Vision 这类模型完成第一轮截图理解。

可以采用混合架构：

```
截图
  -> Gemini / 其他视觉模型分析截图
  -> 生成结构化 UI 描述
  -> DeepSeek 负责代码生成和修改
```

或者：

```
截图
  -> 视觉模型生成分析文本
  -> DeepSeek 读取分析文本生成代码
```

但如果要让 DeepSeek 自己调用 `screenshot_preview` 进行迭代，它至少需要能理解工具返回的截图；否则只能接收：

```
截图的文字描述
布局检测结果
DOM/像素分析结果
```

所以它在这个项目中更适合作为：

```
代码生成 Provider
```

而不一定是完整的：

```
多模态 UI 生成 Provider
```

## 推荐实现路径

如果你要接 DeepSeek，我建议按这个顺序。

### 第一阶段：先测试 OpenAI 兼容性

验证：

```
DeepSeek 是否支持 Chat Completions
DeepSeek 是否支持 function calling
DeepSeek 是否支持流式 tool call
DeepSeek 是否能完成工具结果续接
```

如果当前 OpenAI Provider 依赖 Responses API，而 DeepSeek 不支持，就不要强行塞进去。

### 第二阶段：抽出 OpenAI Chat Completions Provider

建议形成：

```
ProviderSession
  -> OpenAIResponsesSession
  -> OpenAIChatCompletionsSession
  -> AnthropicSession
  -> GeminiSession
```

DeepSeek 先复用：

```
OpenAIChatCompletionsSession
```

### 第三阶段：必要时再添加 DeepSeek 专用适配器

只有在发现 DeepSeek 有协议差异时，才新增：

```
DeepSeekProviderSession
```

这样可以避免一开始为了一个 OpenAI-compatible API 复制一整份 Provider 代码。

------

## 最终判断

可以这样记：

```
DeepSeek 完全兼容当前 OpenAI Responses API
  -> 不需要新 Provider，增加配置即可

DeepSeek 兼容 OpenAI Chat Completions，但不兼容 Responses
  -> 需要新的 Chat Completions Adapter
   或单独 DeepSeek Provider

DeepSeek 的工具调用/流式/推理协议有明显差异
  -> 需要专门 DeepSeek Provider

DeepSeek 不支持视觉输入
  -> 不能单独承担截图理解，需要和 Gemini 等视觉模型组合
```

所以你的原话可以更精确地改成：

> 想在 Screenshot-to-Code 中使用 DeepSeek，需要让它接入现有的 `ProviderSession` 抽象。是否要新写一个 `deepseek provider`，取决于它和当前 OpenAI Provider 的协议兼容程度；业务层和 Agent Loop 不需要重写。
