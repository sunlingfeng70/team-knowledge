## 项目本身其实具备“从截图裁剪资产”的能力

当前仓库确实实现了 `extract_assets` 工具，位置是：

[backend/agent/tools/extract_assets.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/tools/extract_assets.py)

它的设计流程是：

```
输入截图
  -> Gemini 识别截图中的图片位置
  -> 返回 bounding box
  -> 后端按坐标裁剪原始截图
  -> 保存裁剪后的图片
  -> 返回本地 public_url
  -> 模型把 public_url 写入 HTML
```

关键代码逻辑是：

```
saved_asset = await persist_data_url_as_asset(
    data_url,
    asset_base_url,
    user_id=user_id,
)
```

然后把本地访问地址交给模型：

```
public_url = saved_asset.public_url
```

生成的地址通常会是类似：

```
http://127.0.0.1:7001/local-assets/xxxx.png
```

或者生产环境下：

```
http://你的后端地址/local-assets/xxxx.png
```

本地文件默认保存目录由 [backend/config.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/config.py) 决定：

```
LOCAL_ASSET_DIR = os.environ.get(
    "LOCAL_ASSET_DIR",
    os.path.join(os.path.dirname(__file__), "local_assets"),
)
```

也就是默认：

```
backend/local_assets/
```

FastAPI 会把这个目录挂载成：

```
/local-assets
```

对应代码在：

[backend/uploaded_assets/store.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/uploaded_assets/store.py)

```
app.mount(
    "/local-assets",
    StaticFiles(directory=LOCAL_ASSET_DIR),
    name="local-assets",
)
```

## 为什么你的 `4.html` 没有使用这些本地裁剪图片？

从结果推断，最可能是以下几种情况之一。

### 情况 1：没有启用资产提取

`extract_assets` 是否可用取决于：

```
GEMINI_API_KEY 是否存在
isAssetExtractionEnabled 是否开启
输入是否包含截图
```

Provider 工厂里有明确限制：

```
asset_extraction_enabled =
    should_extract_assets and bool(gemini_api_key)
```

也就是说，如果生成时没有 Gemini Key，那么 `extract_assets` 工具根本不会提供给模型。

这时模型只能：

```
直接使用外部 URL
或使用 generate_images
或使用纯 CSS/占位图
```

### 情况 2：模型没有调用 `extract_assets`

即使工具可用，模型也不一定会调用。

系统 Prompt 虽然要求：

```
Use extract_assets when available
```

但最终是否调用，仍然由模型决定。

如果模型认为：

```
我知道这本书的 ISBN，可以直接引用 OpenLibrary
```

它就可能直接写网络 URL。

### 情况 3：模型调用了资产提取，但没有把结果用于最终代码

资产提取工具有可能成功，但是模型后面仍然决定使用外部地址。这属于 Agent 行为问题，不是文件保存逻辑问题。

可以通过生成过程中的 Agent Activity 查看是否出现：

```
Extracting assets
Extracted assets
```

如果没有这些事件，基本可以确定它没调用 `extract_assets`。

### 情况 4：你导出的 HTML 只保存了代码，没有复制资源

即使工具提取成功，导出 HTML 也不一定会把图片物理复制到：

```
生成的代码/
```

当前设计更偏向于：

```
HTML 引用后端 `/local-assets/...` 地址
```

而不是：

```
HTML 和图片一起打包成一个自包含目录
```

所以“生成的代码目录没有图片”本身不能完全说明没有提取过；但你这个文件中的明确 `openlibrary.org` 地址已经说明最终版本没有采用提取后的本地资产。

## 这个项目的资产策略其实是混合的

系统 Prompt 的策略大致是：

```
原图中已有的视觉资产
  -> 优先 extract_assets

原图中没有或无法提取的资产
  -> 可以 generate_images

不要把整张截图当作背景直接嵌入
```

也就是说，设计目标是：

```
真实原图元素：
  尽量从截图裁剪

无法获得的图片：
  才让图片模型生成或让模型使用替代图

布局和页面结构：
  必须用 HTML/CSS 实现
```

但这个策略有一个现实问题：

> 它是通过 Prompt 约束模型，而不是在程序层强制禁止外部图片 URL。

因此模型仍然可能写：

```
https://covers.openlibrary.org/...
https://images.unsplash.com/...
```

程序当前没有一个强制的 HTML 后处理器去：

```
扫描所有 img src
  -> 判断是不是外部图片
  -> 替换成截图裁剪资产
```

所以模型一旦选择了外部 URL，最终 HTML 就会保留它。

------

## 如果你要求“必须保留原图图片”，需要改进什么？

建议至少做三件事。

### 1. 强制资产提取

当输入是截图时：

```
先独立执行资产提取
再把提取结果作为 Prompt 上下文传给代码模型
```

不要完全依赖模型自己决定是否调用 `extract_assets`。

流程改成：

```
截图
  -> 后端先调用 Gemini 做资产检测
  -> 保存所有候选图片
  -> 生成模型只能从这些资产 URL 中选
```

### 2. 禁止模型自行引用外部图片

系统 Prompt 可以加强：

```
所有出现在原始截图中的图片必须使用 extract_assets 返回的 public_url。
禁止使用 OpenLibrary、Unsplash、Pexels 或其他外部图片地址替代原图。
除非用户明确要求联网获取新图片。
```

但只改 Prompt 仍然不是绝对保证。

### 3. 增加生成结果校验

在最终 HTML 返回前扫描：

```
<img src="http://...">
<img src="https://...">
background-image: url(...)
```

如果发现外部图片：

```
再次调用模型修复
或替换为对应的本地资产
或明确提示用户该图片没有使用原图
```

更可靠的是定义允许列表：

```
允许：
  data:image/...
  /local-assets/...
  http://后端地址/local-assets/...

禁止：
  covers.openlibrary.org
  unsplash.com
  images.unsplash.com
  其他任意外部图床
```

## 最终结论

你的判断是对的：

> `4.html` 中的图片没有保存在生成代码目录，也没有使用原始截图中裁剪出来的图片；它最终引用了 OpenLibrary 的网络封面地址。`百年孤独` 变成英文版，是因为模型选择了对应英文 ISBN 的封面，而不是保留原图中的中文版封面。

更精确地说：

```
不是原始 HTML 截图资源
不是本地保存的裁剪资源
不是 Replicate 生成图片
而是模型写入了 OpenLibrary 外链
```

这个项目虽然有 `extract_assets` 的本地裁剪能力，但当前实现是“模型可选工具”，不是“程序强制资产管线”。因此要保证图片一致性，需要把资产提取前置，并对最终 HTML 的外部图片引用做校验。
