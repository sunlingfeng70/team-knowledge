我把仓库按“入口、请求流、模型层、Agent 循环、工具层、前端状态”读了一遍。这个项目的核心思路可以概括为：

> 一个面向 UI 生成的垂直 Agent：接收截图/视频/文字/已有代码，构造多模态 Prompt，让多个模型并行生成代码；模型通过统一的工具协议创建或修改文件、提取截图资产、生成图片、渲染预览，再把中间过程实时推送给前端。

它并不是简单的：

```
截图 -> LLM -> HTML
```

更接近：

```
用户输入
  -> Prompt / 历史 / 文件状态整理
  -> 选择一个或多个模型
  -> 统一 Agent Loop
       -> 模型流式输出
       -> 模型调用工具
       -> 执行工具
       -> 把工具结果回传模型
       -> 继续下一轮
  -> 得到文件状态
  -> 前端实时预览与版本管理
```

以下分析基于当前仓库 HEAD，而不是项目早期版本。

------

## 二、一次生成请求是怎么走的

### 1. 前端通过 WebSocket 发起任务

前端创建：

```
ws://backend/generate-code
```

首次发送的参数包含：

- 生成技术栈
- 输入模式
- 截图或视频
- 用户文字要求
- 当前代码文件
- 历史消息
- 是否启用图片生成
- 是否提取截图资产
- API Key
- 设计系统信息
- 当前是 create 还是 update

前端实时接收这些消息：

```
status
thinking
assistant
toolStart
toolResult
setCode
variantComplete
variantError
error
```

因此前端看到的不是一次性结果，而是一个 Agent 运行过程。

------

### 2. 后端使用 Pipeline 分阶段处理

[generate_code.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/routes/generate_code.py) 中把处理拆成几个阶段：

```
接收 WebSocket
  -> 参数提取与校验
  -> 模型选择
  -> Prompt 构造
  -> 并行执行多个 variant
  -> 汇总结果
  -> 返回完成状态
```

关键阶段包括：

- `ParameterExtractionStage`
- `ModelSelectionStage`
- `PromptCreationStage`
- `AgenticGenerationStage`
- `PostProcessingStage`

这说明它的业务层不是直接把所有逻辑塞到 FastAPI 路由里，而是形成了一个生成流水线。

模型选择会根据已有 API Key 自动组合：

```
只有 OpenAI       -> OpenAI 模型
只有 Anthropic    -> Anthropic 模型
只有 Gemini       -> Gemini 模型
多个 Key 都有     -> 多个模型混合
视频模式         -> Gemini
更新已有代码      -> 固定使用适合更新的模型组合
```

它还会生成多个 variant 并行比较：

```
asyncio.create_task(
    self._run_variant(index, model, prompt_messages)
)
```

也就是说，同一次截图可以同时用多个模型生成多个版本。这是产品质量的重要来源之一，因为它允许用户比较结果，而不是把质量完全押在一次模型调用上。

## 三、使用了什么 AI 引擎

它没有采用 LangChain、LlamaIndex、AutoGen 这类通用框架作为核心，而是自己实现了一套较薄的 Agent Runtime。

### 模型供应商

当前代码直接对接：

- OpenAI
- Anthropic
- Google Gemini
- Replicate 图片模型

对应代码：

- OpenAI：[backend/agent/providers/openai.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/openai.py)
- Anthropic：[backend/agent/providers/anthropic/provider.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/anthropic/provider.py)
- Gemini：[backend/agent/providers/gemini.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/gemini.py)
- Provider 选择：[backend/agent/providers/factory.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/factory.py)
- 模型枚举与映射：[backend/llm.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/llm.py)

模型调用不是通过一个统一的第三方 LLM 网关完成的，而是根据模型类型创建不同的 Provider Session：

```
if model in OPENAI_MODELS:
    return OpenAIProviderSession(...)

if model in ANTHROPIC_MODELS:
    return AnthropicProviderSession(...)

if model in GEMINI_MODELS:
    return GeminiProviderSession(...)
```

因此它的统一性主要在“内部协议”，而不是依赖外部框架。

------

### 支持的模型类型

从代码看，主要有三类：

```
OpenAI:
  GPT 系列

Anthropic:
  Claude Sonnet / Opus 等

Gemini:
  Gemini Flash / Pro 等
```

模型名称和实际 API 名称被分开配置。例如：

```
Llm.GPT_5_5_HIGH
```

内部表示为“GPT-5.5，高推理强度”，然后映射为：

```
{
    "api_name": "gpt-5.5",
    "reasoning_effort": "high"
}
```

这是一种比较实用的设计：产品层不直接依赖供应商模型名，而是把“模型 + 推理档位”作为一个可选择的产品配置。

------

### 没有使用单一“AI 引擎”

这里需要明确一点：

> Screenshot-to-Code 没有一个类似“自己的大模型引擎”。

它的“引擎”由三部分组合而成：

```
底层模型 API
  + Provider Adapter
  + 自己实现的 Agent Loop
```

所以真正值得研究的是它如何组织模型调用，而不是它训练了什么模型。

------

## 四、Agent Loop 是最值得学习的部分

核心循环在：

[backend/agent/engine.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/engine.py)

简化后是：

```
for step in range(max_steps):
    turn = await session.stream_turn(on_event)

    if not turn.tool_calls:
        return finalize_response(turn.assistant_text)

    for tool_call in turn.tool_calls:
        result = await tool_runtime.execute(tool_call)
        emit_tool_result(result)

    await session.append_tool_results(turn, executed_tool_calls)
```

也就是标准的：

```
模型输出
  -> 如果没有工具调用，结束
  -> 如果有工具调用，执行工具
  -> 将工具结果放回对话
  -> 继续请求模型
```

最大工具轮数目前是 30：

```
max_steps = 30
```

同时还会检查生成成本：

```
spent = session.total_cost_usd()
if spent is not None and spent > GENERATION_MAX_COST_USD:
    raise BudgetExceededError()
```

这部分有几个重要设计点。

### 1. Provider 被统一成相同接口

[backend/agent/providers/base.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/providers/base.py) 定义了类似这样的协议：

```
class ProviderSession(Protocol):
    async def stream_turn(self, on_event):
        ...

    async def append_tool_results(self, turn, executed_tool_calls):
        ...

    def total_cost_usd(self):
        ...

    async def close(self):
        ...
```

无论底层是 OpenAI、Anthropic 还是 Gemini，上层 Agent 都只关心：

```
stream_turn
append_tool_results
close
```

Provider 自己负责处理各厂商协议差异。

这是整个架构里非常关键的抽象边界：

```
Agent Engine
    不关心具体厂商格式

Provider Adapter
    负责把厂商 API 转换成统一 ProviderTurn / StreamEvent
```

------

### 2. 流式事件被标准化

Provider 的原始事件被转成：

```
assistant_delta
thinking_delta
tool_call_delta
```

然后 Agent Engine 再将其转为前端事件：

```
assistant
thinking
toolStart
toolResult
setCode
```

所以事件链路是：

```
OpenAI/Gemini/Anthropic 原始流
  -> StreamEvent
  -> Agent Engine
  -> WebSocket 事件
  -> React 前端
```

这样做的好处是，前端不需要知道当前使用的是哪一个模型。

------

### 3. 工具调用不是一次性等结果，而是实时处理

工具调用参数本身也支持流式处理。

例如模型正在生成 `create_file` 的参数时，后端会读取正在增长的 `01-公开区` 字段，并提前把代码片段推给前端：

```
模型还没完成 tool call
  -> 已经收到一部分 HTML
  -> 前端先显示代码预览
```

这就是所谓的 live streamed `create_file` preview。

对用户来说，它会感觉代码正在“边生成边显示”，而不是模型完全结束后才出现结果。

------

## 五、它有哪些工具

统一工具定义在：

[backend/agent/tools/definitions.py](K:/works/028.数产尖刀班/.research-screenshot-to-code/backend/agent/tools/definitions.py)

主要工具包括：

| 工具                 | 作用                              |
| -------------------- | --------------------------------- |
| `create_file`        | 创建完整 HTML 文件                |
| `edit_file`          | 对已有文件做精确字符串替换        |
| `generate_images`    | 调用图片生成模型                  |
| `remove_backgrounds` | 去除图片背景                      |
| `edit_images`        | 图片编辑或放大                    |
| `extract_assets`     | 从截图中裁剪真实 logo、图片等资产 |
| `screenshot_preview` | 用无头浏览器渲染当前页面并截图    |
| `save_assets`        | 保存用户上传的图片                |
| `retrieve_option`    | 获取其他 variant 的完整 HTML      |

这里最值得注意的是，它没有让模型直接输出一个巨大的自由格式字符串，而是要求模型通过工具完成文件操作。

### 初次生成

通常是：

```
create_file
```

并要求模型一次写入完整 HTML。

### 修改已有页面

使用：

```
edit_file
```

而不是重新生成整个文件。

这条规则很重要，因为更新页面时重新生成整个文件会导致：

- 原有交互丢失
- 与用户手动修改冲突
- 代码 diff 太大
- 模型重复犯已经修过的问题

所以它把 create 和 update 分成了不同生成路径。

------

## 六、截图资产提取是一个很聪明的拆分

它没有让主代码生成模型自己凭截图猜所有图片，而是引入了专门的 `extract_assets` 工具。

流程类似：

```
截图
  -> Gemini 识别截图中的真实资产位置
  -> 返回每个资产的 bounding box
  -> 后端裁剪原图
  -> 保存成可引用 URL
  -> 代码模型将 URL 放入 HTML
```

这解决了一个常见问题：

> 视觉模型知道截图里有一个 logo，但并不知道它对应哪个可访问的图片 URL。

它把这个问题拆成了两个任务：

```
Gemini：定位与裁剪真实资产
代码模型：决定 HTML 结构和引用方式
```

README 也明确强调 Gemini 被用于资产提取，Replicate 被用于图片生成、背景移除和图片编辑。

这体现出一个实用原则：

> 不要让一个模型承担所有任务；把视觉定位、代码生成、图片生成拆给最适合的模型和工具。

------

## 七、截图预览形成了“生成-验证”闭环

`screenshot_preview` 会：

```
1. 把当前 HTML 放入无头浏览器
2. 渲染桌面版和移动版
3. 截图
4. 把截图作为工具结果返给模型
5. 模型继续修改代码
```

于是生成过程变成：

```
生成代码
  -> 浏览器实际渲染
  -> 得到视觉反馈
  -> 模型判断偏差
  -> edit_file 修改
  -> 再次预览
```

这是比“让模型自己想象页面是否正确”更可靠的方式。

可以把它理解成一个视觉版的测试循环：

```
代码 -> 实际执行 -> 观测结果 -> 修复代码
```

这部分和普通代码 Agent 的：

```
写代码 -> 跑测试 -> 看错误 -> 修改
```

非常相似，只是它的测试信号是截图像素和布局效果。

------

## 八、前端不是简单结果展示，而是一个版本管理器

前端有项目状态和 commit/variant 概念：

- 每次生成可以有多个 variant
- 每个 variant 可以继续更新
- 生成历史可以回看
- 当前 HTML 可以编辑
- 预览和代码可以切换
- 可以选择某个 variant 继续修改

相关代码：

- 项目状态：[frontend/src/store/project-store.ts](K:/works/028.数产尖刀班/.research-screenshot-to-code/frontend/src/store/project-store.ts)
- 预览：[frontend/src/components/preview/PreviewPane.tsx](K:/works/028.数产尖刀班/.research-screenshot-to-code/frontend/src/components/preview/PreviewPane.tsx)
- Variant UI：[frontend/src/components/variants/Variants.tsx](K:/works/028.数产尖刀班/.research-screenshot-to-code/frontend/src/components/variants/Variants.tsx)

因此它的产品模型不是“一次生成一个结果”，而是：

```
项目
  -> 多次生成
  -> 多个版本
  -> 每个版本有代码、截图、模型、提示词和更新历史
```

这也是它和很多简单的 Screenshot-to-HTML Demo 的本质区别。

# 九、和 Pi 的区别

这里我按你说的 Pi 理解为现在的 `pi-mono` / Pi Agent Harness 项目。

Pi 的仓库分成几个重要包：

```
@earendil-works/pi-ai
@earendil-works/pi-agent-core
@earendil-works/pi-coding-agent
@earendil-works/pi-tui
```

对应：

- 统一 LLM API
- 通用 Agent Runtime
- 面向终端的 Coding Agent
- 终端 UI

------

## 1. 定位不同

### Screenshot-to-Code

是一个垂直领域应用：

```
输入截图 / 视频 / 文字
输出网页代码
```

它的工具和 Prompt 都围绕 UI 生成：

```
create_file
edit_file
extract_assets
screenshot_preview
generate_images
```

### Pi

是一个通用 Agent Harness：

```
输入任意用户任务
模型调用 read / bash / edit / write 等工具
完成通用软件工程工作
```

Pi 的 Agent Runtime 不应该知道：

- 截图是什么
- HTML 怎么生成
- 设计系统是什么
- 如何裁剪 logo
- 如何对比页面视觉效果

因此，两者关系更像：

```
Pi = 通用 Agent 内核 / 编排框架
Screenshot-to-Code = 面向网页生成的专用 Agent 应用
```

------

## 2. Agent Loop 相似，但抽象目标不同

Pi 的核心循环大致是：

```
stream assistant
  -> 发现 tool calls
  -> 执行 tools
  -> 插入 tool result
  -> 继续下一轮
  -> 直到模型结束或收到后续消息
```

Screenshot-to-Code 也是类似的循环。

两者的共同点：

- 流式输出
- 工具调用
- 工具结果回传
- 多轮 Agent
- provider 抽象
- 中止和错误处理
- 状态记录

但 Pi 更通用，支持很多 Agent 级能力：

- steering message
- follow-up message
- session continuation
- 中途插入用户消息
- 可替换的 stream function
- 通用状态管理
- 工具执行生命周期事件
- 更完善的 Runtime / Harness 抽象

Screenshot-to-Code 的循环更窄，主要围绕一次页面生成或更新：

```
最多若干工具轮
  -> 得到最终 HTML
  -> 结束 variant
```

它没有把 Agent Runtime 做成一个可独立复用的通用产品。

------

## 3. Provider 抽象方式不同

Screenshot-to-Code：

```
ProviderSession
  -> stream_turn
  -> append_tool_results
```

Provider 直接实现自己的适配器。

Pi：

```
pi-ai
  -> 统一模型 / 消息 / 流式 API
pi-agent-core
  -> 通用 Agent Loop
coding-agent
  -> read / bash / edit / write 工具和 CLI
```

Pi 把“统一模型 API”单独抽成了包，因此模型层可以被其他应用复用。

Screenshot-to-Code 则把模型配置、Agent Provider、业务流程放在同一个后端项目里，垂直集成更紧。

可以这样理解：

```
Screenshot-to-Code：
业务优先，抽象够用即可

Pi：
内核优先，抽象本身就是产品
```

------

## 4. 工具系统不同

Pi 的工具通常是通用计算机操作：

```
read
bash
edit
write
```

Screenshot-to-Code 的工具是领域动作：

```
create_file
edit_file
extract_assets
screenshot_preview
generate_images
```

Screenshot-to-Code 的工具更像“高层业务 API”，而 Pi 的工具更像“操作系统原语”。

比如：

```
Screenshot-to-Code:
edit_file(path, old_string, new_string)

Pi:
edit / write / bash
```

前者给模型的自由度更小，但更容易控制生成行为。

这带来一个重要取舍：

| 方式         | 优点                     | 缺点                           |
| ------------ | ------------------------ | ------------------------------ |
| 高层领域工具 | 行为可控，容易做产品约束 | 泛化能力弱                     |
| 低层通用工具 | 灵活，适合各种任务       | 模型可能误操作，安全边界更复杂 |

------

## 5. Screenshot-to-Code 的“视觉闭环”是 Pi 默认没有的

Pi 默认关注的是：

```
文件内容
命令输出
测试结果
```

Screenshot-to-Code 增加了：

```
浏览器渲染
桌面截图
移动端截图
视觉反馈
```

这可以看成是在 Pi 类 Agent Loop 上增加了一个领域专用验证器：

```
screenshot_preview = UI 生成领域的测试工具
```

如果你要做自己的系统，值得借鉴的不是复制它所有代码，而是把领域验证器抽象出来：

```
DomainValidator:
  execute current artifact
  collect observable result
  return structured feedback
```

在网页生成里是浏览器截图；在报表生成里可以是 Excel 预览；在 PPT 生成里可以是渲染后的幻灯片截图。

# 十、和 OpenClaw 的区别

OpenClaw 是完全更高一层的系统。

它的定位是：

```
运行在用户设备上的个人 AI 助手
```

核心架构是：

```
Gateway
  -> sessions
  -> channels
  -> model providers
  -> tools
  -> plugins
  -> control UI / CLI / TUI
```

README 对它的描述很明确：

- Gateway 是 sessions、tools、events、channel connections 的本地控制平面
- 支持 WhatsApp、Telegram、Slack、Discord、iMessage 等渠道
- 模型、工具、技能和插件可以替换
- 状态、记忆和凭证保存在本机

------

## 1. 产品边界不同

### Screenshot-to-Code

```
一个网页代码生成产品
```

主要输入：

- 截图
- 视频
- URL
- 文字
- 现有 HTML

主要输出：

- HTML/CSS/React/Vue 等网页代码

### OpenClaw

```
一个长期运行的个人助手平台
```

主要关心：

- 消息渠道接入
- 会话管理
- 身份和权限
- 长期记忆
- 多设备
- 插件
- 调度
- 工具安全
- 多用户/团队部署
- 本地 Gateway

因此 Screenshot-to-Code 更像一个“任务型应用”，OpenClaw 更像一个“助手基础设施”。

------

## 2. OpenClaw 的核心不是代码生成，而是 Gateway

OpenClaw 的中心组件是 Gateway：

```
外部消息渠道
  -> Gateway
  -> 会话路由
  -> Agent Runtime
  -> 模型和工具
  -> 返回对应渠道
```

Screenshot-to-Code 的中心组件是生成 WebSocket：

```
前端
  -> generate-code WebSocket
  -> 一次生成任务
  -> 返回页面代码和 UI 事件
```

两者最大的结构差异：

```
Screenshot-to-Code：
一次请求 -> 一次或几次页面生成

OpenClaw：
长期运行 Gateway -> 多会话、多渠道、多任务
```

------

## 3. OpenClaw 的状态模型更重

Screenshot-to-Code 也有历史和 variant，但状态主要是：

```
项目
  -> HTML 文件
  -> 生成历史
  -> variant
  -> prompt history
```

OpenClaw 的状态还包括：

```
用户身份
会话
渠道
权限
凭证
记忆
插件状态
后台任务
子 Agent
设备连接
```

如果你研究的是“如何实现一个截图转代码工具”，OpenClaw 的会话和渠道系统大多不是必需的。

如果你研究的是“如何做一个长期运行的企业级 AI 工作台”，OpenClaw 的 Gateway、session、plugin、policy 才是重点。

------

## 4. OpenClaw 更强调安全边界

Screenshot-to-Code 默认是面向单用户的本地/托管 Web 应用，工具主要是：

```
写 HTML
生成图片
截图
处理资产
```

OpenClaw 需要面对：

```
陌生聊天用户
外部消息渠道
本机文件
Shell 命令
长期凭证
多个用户
远程暴露
插件代码
```

所以 OpenClaw 强调：

```
trusted Gateway
untrusted execution
deterministic policy
pairing / allowlist
sandboxing
tool audit
```

这一点是两者很大的分水岭。

# 十二、这个项目最值得研究的实现思路

如果你主要是想研究“怎么做类似系统”，我认为有六个最值得借鉴的点。

## 1. 把模型能力包装成业务工具

不要只给模型一个：

```
请生成代码
```

而是提供明确工具：

```
create_file
edit_file
extract_assets
screenshot_preview
generate_images
```

这样模型输出从自由文本变成了结构化动作。

------

## 2. 把首次生成和后续修改分开

首次生成：

```
create_file
```

后续修改：

```
edit_file
```

这比每次都重新生成整份代码稳定很多。

------

## 3. 用 Provider Adapter 隔离模型差异

你不需要让业务代码分别处理：

```
OpenAI tool call
Anthropic tool use
Gemini function call
```

统一为：

```
ProviderTurn
StreamEvent
ToolCall
ToolResult
```

这是支持多模型的关键。

------

## 4. 工具定义只维护一份

代码里定义了统一的 `CanonicalToolDefinition`，然后分别序列化为：

```
OpenAI tool schema
Anthropic tool schema
Gemini tool schema
```

这个设计比给每家模型复制一套工具定义更不容易漂移。

------

## 5. 生成结果必须能被真实执行和观测

不要只看模型说“代码应该正确”。

应该：

```
写文件
  -> 启动浏览器
  -> 截图
  -> 把截图交给模型
  -> 继续修复
```

这是一个非常通用的 Agent 设计模式：

```
生成 -> 执行 -> 观测 -> 修复
```

------

## 6. 多模型并行比单模型盲目加 Prompt 更实用

它会根据 API Key 选择多个模型并生成多个 variant：

```
Variant 1: Gemini
Variant 2: Claude
Variant 3: GPT
```

这种方式的产品收益很直接：

- 用户可以比较
- 不同模型擅长点互补
- 降低单次生成失败的风险
- 可以选择一个版本继续迭代

------

# 十三、如果你要自己实现，建议的最小架构

可以从一个比它更小的版本开始：

```
frontend
  React
  WebSocket
  代码/预览双栏

backend
  FastAPI
  /generate WebSocket

core
  PromptBuilder
  ModelRouter
  ProviderAdapter
  AgentLoop
  ToolRuntime
  FileState
  PreviewRunner
```

第一版只需要五个工具：

```
create_file
edit_file
read_file
screenshot_preview
finish
```

流程：

```
1. 上传截图
2. 构造多模态 Prompt
3. 调用模型
4. 模型调用 create_file
5. 浏览器渲染
6. 模型调用 screenshot_preview
7. 模型调用 edit_file
8. 返回最终 HTML
```

第二阶段再加：

```
extract_assets
generate_images
多模型 variant
版本历史
设计系统
成本统计
```

第三阶段才考虑：

```
长期 Session
插件系统
多渠道
权限和沙箱
Gateway
```

换句话说：

- Screenshot-to-Code 告诉你如何做“垂直领域 Agent”
- Pi 告诉你如何做“通用 Agent Runtime”
- OpenClaw 告诉你如何做“长期运行的 AI 助手平台”

如果你的目标是研究截图转代码，最合适的技术路线不是直接照搬 OpenClaw，而是：

```
Screenshot-to-Code 的领域工具
+ Pi 的 Agent Loop / Provider 抽象
+ OpenClaw 的 Session / Policy 思路
```

但三者要分层使用，不能把 Gateway、多渠道、长期记忆等基础设施过早塞进一个截图生成器里。
